# 真实 API 与可用性测试报告

> 历史记录：本文保留早期四样本测试时的结论与数据。后续本地检索与50张跨领域测试见 [新报告](50张跨领域知识库测试报告.md)，不要将本文当时的功能缺口当作当前版本状态。

测试日期：2026-09-12。环境：Windows、Python 3.12、项目源码与独立安装的 wheel。

## 可用性结论

**本轮支持带人工审核的内容整理试用，尚未验证知识库生产质量。** 本次四个正常生成样本按当时的内容整理标准对照来源，三个判为合格，一个需要小幅但实质性的内容修正。轻微重复和编辑提示残留没有被当作不合格理由。这一“三个合格、一个需修改”的结果只反映本轮内容整理测试，不能推导为知识库知识单元合格率。

项目目标是产出供知识库检索与问答使用的知识单元。读者可读只是底线，还需要独立自包含、实体与版本明确、适用条件完整、来源可核对，并能支持相关问题的回答。本轮没有在目标知识平台入库、检索和问答，未测召回效果及回答准确性；也未按本次定位调整后的 `knowledge_card` 1.1 标准重新生成并验收样本。

当前应保留逐卡人工审核：生成器可能把科普简化过度泛化，使用同一模型的审计也可能漏过；自动修复并不保证一次收敛。正常样本的生成加审计耗时约 2.4～5.2 分钟，适合批处理式使用，对即时响应有要求时体验不足。四个样本不足以推算通用领域准确率。

## 本轮采用的内容整理判断标准

目标是“能够合格使用”，不要求文字完美。关键事实错误、遗漏会改变结论的条件、凭空补充知识，以及流程放行明显错误，都属于实质问题；轻微重复、措辞不够精炼、少量编辑提示残留属于改进项。

内容检查由另一个审查代理逐条对照原资料完成，没有把生成模型自己的审计通过当作质量结论。这仍是 AI 辅助审查，不代替最终使用者的人工批准。

上述是原测试的判断口径。后续知识库验收还须检查知识片段能否脱离原文独立理解，实体、版本或时间范围是否明确，会改变结论的条件与例外是否紧邻对应事实，并通过目标平台的实际问题检查召回和回答。本报告保留历史结果，不把新增要求记为已测试通过。

## 真实网页补充测试

选用 [NASA Space Place：What Is a Light-Year?](https://spaceplace.nasa.gov/light-year/en/)，测试英文公开资料整理成中文知识卡。页面正文标注文章更新于 2020-08-27；采集日期单独记录为 2026-09-12，不把页面整体页脚日期当作文章更新时间。

直接网页导入在当前网络环境失败：域名被解析为 `198.18.0.112`，属于非公网地址，采集器拒绝继续。这次失败发生在模型调用前。保留公网地址校验，另行下载该确定的公开网页、提取正文，作为本地 Markdown 输入。此替代路径不能计为“网页直采通过”。

本地资料路径的生成、审计和本地工作区持久化均完成；这里的保存不代表向外部知识平台入库。数字翻译及近似值保留正确，没有把来源中的历史最远纪录写成当前纪录。

但 `key_points` 第三条把“距离多少光年”直接概括成“看到多少年前的样子”，并进一步用于 GN-z11 等遥远星系。该表述缺少距离口径限制：宇宙膨胀会使当前距离与光传播时间不同。NASA 自己的[专家解释（2025-05-21）](https://www.nasa.gov/science-research/astrophysics/how-big-is-space-we-asked-a-nasa-expert-episode-61/)明确说明了这一点。这个问题被生产模型的审计漏过，故不能按“机审通过”直接判成内容合格。

**最小修正建议：** 删除第三条泛化公式，并按任务目标只保留太阳光约 8.3 分钟的例子，删除“其他天体”一条。原始版本保留在待审核，未静默修改不可变版本、未代替用户批准。无需为重复章节标题或轻微冗余另开大改。

## 失败分支与人工审核

另建隔离工作区，以本地构造的错误候选验证真实 API 的审计与修复：故意写成“两类完全互斥”和“相近词在所有句子中都能任意替换”。初始候选并非真实模型生成，不能计入生成质量样本。

审计正确返回两条 ERROR，明确指出与来源相反的表述。修复只改动目标 `key_points`，恢复了定义口径、非互斥及按上下文判断等内容。

重审连续两次 180 秒超时，第三次得到响应，但仍判失败：指出“可以观察”被强化为“需要观察”，以及原先仅针对“开心／高兴”的例句结论扩大到全部例句。前者偏严格，后者有范围泛化问题。达到一次修复预算后，工作流正确停在 `STOPPED`，未绕过审计进入人工批准。

本项验证了**错误拦截、定点修复、重审、重试上限和失败停止**，但“自动修复后重审通过”这个成功闭环在本次真实测试中**没有实现**，不可标记为通过。共 5 次真实调用尝试，3 次返回响应、2 次超时，714.42 秒，已报告 30,082 tokens。不能根据一个反例推算修复成功率，也不应把人工看来轻微的问题一概视为可忽略的事实差异。

正常样本均没有人工审核记录、批准、发布或验收记录。页面展示正文与通过／退回选项，未批准时导出、发布和验收操作禁用。

所有有用量回执的 11 次真实 API 响应合计 **107,022 tokens**。另有两次超时和首轮中断请求没有用量回执；实际计费可能更高，本报告不估算金额。到此结束本轮调用，没有继续扩大样本或反复重生成来追求全绿。

## 本轮发现并修复的运行问题

1. **Windows 中断任务恢复。** 原实现以 `os.kill(pid, 0)` 探测进程。它在 Windows 上不能当作只读存活检查，还可能造成异常或终止目标进程；已改用 Windows 进程句柄与零超时等待。真实子进程测试证实第二工作台扫描不会终止任务，进程退出后会回收中断任务及锁。参见 [Python 对 Windows os.kill 的说明](https://docs.python.org/3/library/os.html#os.kill) 和 [Windows 等待接口说明](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject)。
2. **安装包默认示例缺失。** 修复前，项目外运行已安装 wheel 的 demo 因缺少仓库 examples 失败。已将独立最小离线样例随包分发，并保留 `--example-root` 自定义资料入口。

全套 **24 项测试通过，无跳过**。覆盖真实子进程恢复、独立 wheel 安装、默认及自定义 demo、结构合同、引用、选填段落、修复、版本与人工审核绑定等。此处的生命周期和安装回归使用 mock，不算真实模型质量证据。

Playwright 页面检查确认：真实任务从生成自动推进到审计和待人工审核；切换不同卡片后正文与状态匹配；控制台没有错误。命令行新建的任务需要先在工作台刷新列表才能发现，这与已选中运行任务的自动进度同步是两件事。
